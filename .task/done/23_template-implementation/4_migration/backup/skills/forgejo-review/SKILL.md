## Наблюдение

```bash
python3 ~/.pi/agent/skills/forgejo-review/review.py --notify &
```

Запуск из bash-панели pi-сессии: скрипт берёт `PI_INTERCOM_SESSION_ID`
из env. Scope наблюдения — задаётся явно, три формы:

- `--notify owner/repo` — все открытые PR репозитория;
- `--notify owner/repo#N` — один PR;
- `--notify` (без аргументов) — все открытые PR всех репозиториев аккаунта.

Нотификатор запускается, когда известен репозиторий с MR'ом (обычно —
тот, в котором ведётся работа); сам по себе он не решает, за чем следить.

Скрипт живёт до закрытия pi-сессии (запас 5 минут) и завершается сам;
после перезапуска сессии запускать заново. Доставленное не дублируется:
слепк доставленных лежит на диске, перезапуск не рассылает известное.
Код 1 на старте — нет `PI_INTERCOM_SESSION_ID` или API/брокер
недоступны; код 1 в работе — сбой доставки уведомления.

## Формат сообщения

На каждое новое комментирование — блок на комментарий: строка
`[метка] адрес — текст` и под ней hunk-окно диффа с `>>` на
закомментированной строке или `ошибка: …`:

````text
[NikolayXHD/sandbox#3] README.md:131 + — вопрос
    @@ -128,1 +128,4 @@
    ```

    fj-test marker 1
>> fj-test marker 2
[NikolayXHD/sandbox#3] mr — общий вопрос по MR
````

Адрес комментария — между меткой и «—». Код-коммент: путь к файлу,
номер строки и знак стороны (`+` — новая, `-` — старая); общий комментарий
— `mr`. Mетка — `owner/repo#номер-MR`.

Hunk — из сырого diff'а MR (`.diff`-роут, с rename-детекцией): у
переехавшего файла помётка `переехал из <старый путь>` и настоящий
hunk с изменёнными строками (сохранённый forgejo'й diff_hunk показывает
переезд как «файл создан» и теряет изменения). Фолбэк — сохранённый
`diff_hunk` комментария: для комментариев на неизменённые строки
(в diff'е hunk'а нет) и при сбое fetch'а diff'а; если и он пуст —
строка `ошибка: …` (явный сбой, не тихий пропуск: сообщи
пользователю).

Черновые (PENDING) комментарии не доставляются: ревью считается
наброском до submit. Вся пачка комментов приходит одним сообщением
сразу после submit-а ревью; общие комментарии MR (не в ревью) —
сразу.

## Создание PR

```bash
python3 ~/.pi/agent/skills/forgejo-review/review.py --pr \
    --source-branch <ветка> --target-branch <ветка>
```

Создаёт PR в репозитории, чья рабочая копия в cwd (репо — из URL
remote origin, владелец — от токена): исходная и целевая ветки
всегда явные, умолчаний нет. PR
создаётся от имени `pi-agent` (автор — он). Для приватных репозиториев
нужна write-доступность pi-agent к репо. Выход:
`owner/repo#N` (адрес для --notify/--reply) и URL.

## Ответ

Отвечай на комментарии только через `review.py --reply`. Текст реплики —
в файл, передаёшь ссылкой, shell не участвует:

```bash
python3 ~/.pi/agent/skills/forgejo-review/review.py --reply <адрес> @<файл-текста>
```

Адрес: метка MR + адрес из строки блока, как есть. Формы:
`NikolayXHD/sandbox#3 README.md:131 +` (ответ в тред код-коммента),
`NikolayXHD/sandbox#3 mr` (общий комментарий MR). Простой однострочный
текст можно передать без файла: `"текст"`.

Ответ на код-коммент кладётся в тред исходного комментария — в том же
ревью, на той же строке (штатный механизм; работает после submit
ревью). Пока ревью PENDING, оно невидимо pi-agent — ответ уходит
отдельным COMMENT-ревью на той же строке, после submit его можно
перенести. Все ответы уходят под аккаунтом `pi-agent` (не от имени
владельца репозитория) — в UI они видны как реплики другого
участника.

## Аккаунты

- `token` — токен владельца (чтение: наблюдение, список);
- `agent_password` — пароль аккаунта `pi-agent` (ответы, Basic-auth).
Файлы секреты, 600; не коммитить, не выводить в чат.

## Протокол правок по ревью

- Предложи решение
- Получи одобрение пользователя
- Вноси правки

## Посмотреть полный список комментариев

```bash
python3 ~/.pi/agent/skills/forgejo-review/review.py --list
```

Все живые комментарии всех открытых MR (или явных целей `owner/repo#N`),
в порядке чтения. Это путь восстановления после самостоятельного выхода
нотификатора.

## Оформление реплик

Изложение должно быть внятным, тезисы на отдельных абзацах.
