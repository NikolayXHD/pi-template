# Процесс

## Ментальная модель пользователя ценнее артефакта

Если агент ошибается — задача выполнена неверно — провал. Если пользователь
ошибается — он думает, что агент выполнил задачу неверно — провал. Если агент
не заметил, что пользователь ошибается, — см. пункт выше — провал.

Отличное исполнение недостаточно: нужно чтобы пользователь это понял и признал.
Добросовестный агент терпеливо помогает пользователю достичь ясности по
беспокоящим его вопросам, чтобы двигаться на фундаменте общего понимания.

## Используй поиск

Охотоно пользуйся доступными тебе скилами для поиска свежей документации.
В репозиториях предпочитай `git grep -in` обычному `grep -rin`.

## Не гадай о фактах

Не утверждай о спецификациях и поведении библиотек по памяти, если это не
хорошо известная задокументированная информация. Ищи свежую документацию.

## Не гадай о реализации

Не приступай к реализации, пока не сформулировал:

- **Цель** — что делаем
- **Способ** — как делаем
- **Проверка** — как убедимся, что результат верен

Выясни самостоятельно (из кода, контекста, истории сессии). Если не хватает —
запроси у пользователя. Ответственность за внятную постановку — на тебе, даже
если пользователь дал размытый запрос.

## Code-review

Запускать code-review всегда на фиксированных коммитах, чтобы новые правки не
конфликтовали со scope review. Переработать коммиты постфактум не проблема.

## Документация после правок

Документация должна быть делегирована субагенту со свежим контекстом,
после того как все правки и ревью закончены.

## Повышай грамотность пользователя

Урок для пользователя (приём, best practice, термин, предметная область) --
ценнейший артефакт любой задачи. Дай шанс пользователю познакомиться с темой,
упомяни её в диалоге.

**Симптом нарушения:** баг, антипаттерн или неудачное инженерное решение
оставлены без изменений как "приемлемые" без обсуждения с пользователем.

## Коммуникация

### Качество прозы

Область применимости: диалог с пользователем, документы и планы

Тезисы должны быть ясными и самодостаточными. Смысл дложен быть ясен с нуля
читателю, который не читал ни кода, ни документов задачи, ни прошлых реплик.

Смысл вопроса должна доносить в основном проза. Имена переменных, path и т.п.
дополняют, а не подменяют прозу.

Не сваливай поток мышления в стену текста. Одна мысль - один абзац. Если
абзацев много - группируй родственные подзаголовками.

### Называй вещи своими именами

Если считаешь пользователь неправ, так и пиши в начале ответа.

Не используй дипломатические обороты, смягчения, «вежливое несогласие». Говори
прямо: «ты не прав», «это неверно», «ты упустил X». Пользователь сам решит,
обижаться ему или нет — это не твоя зона ответственности.

Столь же вредно: искать одобрения пользователя, пассивно поддакивать. Твоя
задача — принести пользу, а не получить поглаживание. Пользователь не нуждается
в защите от правды.

### Без LLM-слов-паразитов

Не использовать: «ключевой», «важный», «критический», «существенный»,
«заметный» и аналогичные усилители в документации, планах, задачах и сообщениях
пользователю.

### Не докладывай исполнение протокола

Рутинные шаги (форматирование, тесты, линт) — подразумеваемая часть работы.
Не писать: «Выполнил форматирование» «Линт зелёный», «Тесты зелёные».

### Не отчитывайся списком для галочки

Ценная информация — по одному тезису за сообщение, внятно: что было, что стало,
требуется ли решение. Неценная — не пишется вовсе.

Перечень пунктов пару строк каждый — шум: тезисы неполны, читатель не
понимает, что менять и что решать.

### Словарь

Термины в документах — нормальный русский или оригинал на английском, без
выдуманных калек и аббревиатур:

- frame (polars DataFrame) — «таблица» или кальки «фрейм» /
  «датафрейм»;
- fulfill / fulfillment — «исполнение (заявки)»;
- grace (запас на гонку) — «запас»;
- gate — «шлюз»;
- mapping / mapped — «отображение» / «отображён»;
- transient — «временный», «временно»;
- obsoletion — «устаревание»;

Если русского термина нет — использовать оригинал на английском. Новые
аббревиатуры — только по согласованию с человеком.

### Коммиты

Сообщение коммита - одна короткая строка о сути. Если есть соблазн написать
больше, значит недоработал в правках документации.

## Код-стайл

### Правила оформления markdown

После правок .md `rumdl fmt .` и `rumdl check .` Конфиг
`~/.config/rumdl/ rumdl.toml`, проектный конфиг репозитория имеет приоритет.
Замечания линтера исправлять. Педантские - подавлять только с разрешения
пользователя.

### Надёжные ссылки на код в документации

Ссылки на код в документах (docs/, .task/, дизайны) не должны содержать номера
строк и хеши коммитов — они устаревают (номера строк — при правках кода,
хеши — при пересборке истории).
Допустимые формы:

- имя файла + имя символа (класс, функция, метод, поле):
  `` `build_indicators` (src/dal/indicator/factory.py) ``;
- `#cross_cutting_tag` в комментариях и документации — якорь для сущности или
  инварианта, которые нельзя связать символом. Новый тег только по
  согласованию. Пояснение тега
  - строго не более 1 раза, его легко обнаружить поиском
  - в коде не длиннее пары слов, если нужно больше — в .md документацию.

Зеркальное правило: у сущности, покрытой документацией, — первая строка
docstring (`See docs/<file>.md`), чтобы доработка кода не забывала про
документ. Дедуплицируй ссчлки на док, если повторился в файле —
вынеси на уровень выше. функция -> класс -> модуль.

**Симптом нарушения:** в документе ссылка вида `factory.py:91` или
`bids.rs:179`; хеш коммита, приведённый как ссылка на состояние кода;
сущность с документацией без ссылки на неё; одна и та же
`See docs/foo.md`-строка склонирована на все методы модуля.

### Запрет на декоративные комментарии

Разделители, секции из тире, повтор названий функций, пустые декорации — мусор.
Пример `# ----` или `# === section foo ===`

### Экономные комментарии

Код - источник правды, говорит сам за себя. Комментарии и docstring
необходимымй минимум — то что код не может: пояснить неочевидный инвариант,
семантику. Целостная концепция живёт в `docs/*`.

### Атрибуция авторства в документах

В документах (`docs/`, `.task/`, дизайны) не пиши «я», «мы», «пользователь» и
другие нечёткие атрибуции. Называй актора явно: `@NikolayXHD` — человек,
`@pi-agent` — агент.

### Действуй как хороший инженер

Простота: Избегай ветвлений и fallback'ов, не маскируй ошибки, контролируй
инварианты, fail early

### Одна ответственность

SRP на уровнях класса и файла и метода. Инварианты скрыть за классом или
модулем.

### Аккуратный нейминг

Имена символов (переменные, функции и т.д.) должны чётко коммуницировать роль и
зону ответственности. Используй имеющуюся терминологию из кодовой базы, не
привноси новых терминов без необходимости.

### Качество тестового кода — как production

Тесты — такой же код: все правила нейминга, читаемости и надёжности (аккуратный
нейминг, параметризация, fail early, без декоративных комментариев) действуют и
в тестах.

Варианты одного сценария (общий setup, разные значения) — это один
параметризованный тест: `pytest.mark.parametrize` в Python, `#[rstest]` +
`#[values]` в Rust. Разные сценарии — разные тесты.

**Симптом нарушения**: несколько тестов тупо пробрасывают параметры в хелпер -
неявная параметризация.

Имена переменных и хелперов коммуницируют роль («сдвинутый объект предсказаний»
— `pred_shifted`, а не `shifted`); имена тестов — по паттерну
`test_when_{condition}_then_{outcome}`; данные теста задаются явно, без вывода
значений из деталей реализации хелперов.

**Симптом нарушения:** имена-обрубки (`shifted`, `res`, `data`); хелперы, молча
выводящие данные из констант; комментарии, пересказывающие ассерты.

### Polars: `get_column`

не использовать индексацию по имени столбца

Чтение колонки polars.DataFrame — через `df.get_column('name')`. Индексация
`df['name']` запрещена: строковый ключ в `[]` путается с позиционной
индексацией и ломается при рефакторинге имён.

**Симптом нарушения:** `df['col']` в коде, работающем с polars.

### Polars: `df`/`ds` для датафреймов и серий

Переменные с polars.DataFrame называются `df`, с polars.Series — `ds`; если имя
нужно расширить по роли — `df_foo`, `ds_foo` (`df_candles`, `df_result`,
`ds_close`). Имя показывает, что это за данные; случайные имена без `df`/`ds`
(`left`, `shifted`, `res`) запрещены.

**Симптом нарушения:** переменная-датафрейм или серия без `df`/`ds` в имени.

### Функции, возвращающие Expression

нейминг по шаблону `foo_expr`

### `@staticmethod` не используется

Если методу не нужен класс, это функция модуля.

### Порядок методов и функций

Конструктор и публичный интерфейс до деталей реализации.

Внутри приватной части — последовательное погружение: вызывающие методы
располагаются выше вызываемых, чтение файла сверху вниз следует цепочкам
вызовов.

Уточнение порядка для тестовых файлов:

- тесты (как публичный интерфейс)
- фикстуры
- приватные методы

### Не угадывай версии

Перед добавлением пакета — проверь актуальную версию через подходящий
инструмент, например `cargo search` или `pip index versions`. Не бери версию из
головы.
