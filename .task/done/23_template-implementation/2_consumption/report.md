## Поведение по стадиям

### B.1. Версии и сверка

- В памяти две версии (`versions.ts` → `ContextVersions`): **применённая**
  (`applied`) и **актуальная** (`current`); тексты и view каждой.
  Расхождение текстов — статус «промпты отстали» (`isStale()`).
- Отпечатки источников — `mtimeMs:size` (`sourceStamps`/`stampsDiffer`),
  в набор входят и источника `X.template`, и файлы реестра партиалов
  (правка `roles/**` тоже перерисовывает актуальную версию).
- На каждом `before_agent_start` — повторное обнаружение источников и
  сверка отпечатков (`session.refreshSources`): изменилось — актуальная
  перерисовывается **без пересчёта вычисляемых**; применённая и зеркала не
  трогаются.
- Явные действия: `setVariable`, `recompute`, `recomputeAll`, `apply`
  (API зоны C). Правка источника, смена переменной и модели/уровня только
  перерисовывают актуальную и помечают контекст устаревшим.
- После `/reload` новый экземпляр принимает зеркала за применённую версию
  (`start(reason: "reload")` → `applied := startupTexts`) и рендерит
  актуальную заново; при совпадении текстов `isStale()` = false.

### B.2. Лок

- `lock.ts`: каталог `<зеркало>.lock` и `owner.json` `{token, pid, at}`;
  форма (mkdir) и имя — деталь реализации.
- Повторный вход: `acquireLock` того же процесса по тому же пути
  увеличивает глубину и возвращает тот же токен; освобождение на глубине
  > 1 только уменьшает счётчик.
- Короткое владение: маркер старше `LOCK_TTL_MS` (10 с) считается
  протухшим и снимается следующим желающим; занятый свежий лок ожидается
  `LOCK_WAIT_MS` (1.5 с), затем попытка отказывается (`null`).
- Запись зеркала (`writeMirrorUnderLock`) и снятие (`releaseLock`) — только
  при подтверждённом владении (токен маркера на диске): утративший
  владение не пишет и чужой лок не снимает; скобки чтения/спавна при
  `lost` повторяют перерисовку (до двух попыток).
- Скобки держат локи до `tool_execution_end` (не `tool_result` — на
  immediate-путях его нет); `session_shutdown` снимает только свои скобки.

### B.3. Доставка в промпт

- `session.beforeAgentStart` мутирует `event.systemPromptOptions`:
  `contextFiles`, `skills`, `customPrompt`, `appendSystemPrompt`.
  Форс `systemPrompt` не используется (и не нужен).
- Применение — только явное: старт сессии (запись зеркал на
  `session_start`, доставка на первом `before_agent_start`), сверка
  фактической модели на первом ходу, кнопка `apply()` (API зоны C),
  `/reload` (запись актуальной версии на `session_shutdown` до
  перечитывания зеркал pi).
- Правило доставки для каждого нашего зеркала: **замена**, если запись с
  нашим путём уже есть у pi (зеркало прочитано до `session_start`), либо
  **добавление**, если записи нет (зеркала не было к моменту загрузки pi —
  первый запуск после миграции). Порядок и форма — как у pi:
  - `contextFiles` — глобальный каталог агента, затем предки cwd снаружи
    внутрь, по одному кандидату на каталог (`CONTEXT_CANDIDATES`);
  - `skills` — только зеркала `SKILL.md`, отсутствующие у pi; запись
    `{name, description, filePath, baseDir, sourceInfo, disableModelInvocation}`,
    `name` из frontmatter, иначе имя каталога (как `loadSkillFromFile`);
    проектные скилы добавляются только при trust;
  - `customPrompt`/`appendSystemPrompt` — замена опознанного зеркала;
    пустая секция дополняется текстом источника, который pi выбрала бы
    (проектный `.pi/…` при trust, иначе агентский каталог).
- Чужие записи не трогаются: производный текст (строка CLI, эффективный
  промпт ребёнка, чужой контекстный файл) остаётся как есть. Опознание
  секции — по стартовому или применённому тексту нашего зеркала.
- «Зеркало исчезло» (удалён `X.template`): источник выпадает из версии,
  запись pi остаётся как есть — `X` стал обычным файлом пользователя.

### B.4. Чужие чтения

- `tool_call` с `read` и путём, совпавшим с зеркалом нашего источника:
  лок → рендер источника под view **применённой версии** → запись при
  расхождении; лок держится до `tool_execution_end` (там снятие с
  проверкой владельца). Встроенный read не переизобретается и не
  подменяется; вложенные `executeTool` проходят те же перехваты
  (`toolCallId` — ключ скобки).

### B.5. Спавн

- `tool_call` с `subagent`: цели собираются обходом аргументов без
  привязки к схеме — каждый объект со строковым полем `agent`; `model`
  из того же объекта, иначе наследуется от объемлющего. Для каждой цели
  лок + двухэтапный рендер агентского файла (`renderAgentFile`): шапка
  итерациями до фикс-точки, `model`/`level` из YAML (шов `agent.ts`),
  тело — с фактическими; запись при расхождении. Суффикс `:level` в
  `model` разбирается по `THINKING_LEVELS`.
- Имена целей не нашлись (workflow-скрипт, неразобранная форма, иная
  схема) — под локами перерисовываются **все** агентские зеркала
  дефолтами сессии; неточность `model@` в неразобранных формах —
  допустимое приближение.
- Перерисовка без спавна — тот же код с дефолтом сессии вместо параметров
  спавна (`renderSourceSet` → `renderSources` на каждом пересчёте).
- Известное ограничение design (m1): порядок обработчиков `session_start`
  с pi-subagents не гарантирован; каталог advertised может держать прошлое
  зеркало до следующего обновления — наша запись агентских зеркал идёт на
  `session_start` (до или после обновления pi-subagents).

### B.6. Идентичность субагента

- `identity.ts`: тег `<active_agent name="…"/>` из `ctx.getSystemPrompt()`
  на `session_start` (и повторная проверка на первом `before_agent_start`
  для pane-native); запасное — имя сессии: точное имя агента или
  `agent: <выдержка>`; бесформенное имя — агент неизвестен, `@`-ключи не
  применяются. Запасной канал даёт громкое предупреждение. Появление
  имени у сессии без тега (`session_info_changed`) — тот же запасной
  канал: `@`-значения пересчитываются в актуальной версии, применённая не
  меняется (контекст помечен устаревшим).
- Значения `@`/`@<имя>` — из конфига через движок: `computeView` получает
  `agentName`, цепочка `@<имя>` → `@` → `initial`/вычисление. Для
  pane-native тег ловится на `before_agent_start`, view пересчитывается и
  применяется тем же ходом.

### B.7. Регистрация и провалы

- `registerRequiredChildExtensions` (`pi-subagents/required-child-extensions`)
  на `sessionId`, без `requireForAllRunners`: резолв — bare-импорт, затем
  `createRequire.resolve` по npm-корням pi (`<agentDir>/npm/node_modules`,
  `<project>/.pi/npm/node_modules`); не нашлось — одно громкое
  предупреждение и работа без регистрации. Machine и внешние CLI не
  обходятся и не маскируются.
- Провал рендера файла — зеркало не переписывается: в версии остаётся
  прежний успешный текст (кэш = содержимое зеркала), предупреждение
  называет источник и причину. Битый `template.json` — view не строится,
  перерисовки нет; отсутствие `model`/`level` — предупреждение, view
  достраивается на первом ходу, если значения появились.

## API для зоны C

Методы `TemplateSession` (создаётся в `index.ts` на сессию; зона C
получит экземпляр из карты сессий и вызовет их из `/template`):

- `ready()`, `isStale()`, `currentView()`, `currentValues()`,
  `sessionProblems()`, `sessionWarnings()`, `computedAge(name)` — статус
  и данные меню;
- `apply()` — кнопка применения: актуальная → применённая, запись зеркал,
  доставка на следующем `before_agent_start`;
- `setVariable(name, value)` — смена сессионной переменной (запись
  `"var"` — на стороне зоны C); вычисляемые и неявные отвергаются;
- `recompute(name)`, `recomputeAll()` — явный пересчёт вычисляемых
  (цепочка объявлений до указанной переменной; возраст значения
  обновляется).

## Проверка производного текста промпт-шаблонов (по коду pi)

Что лежит в секциях к моменту обновления (`before_agent_start`):

- `AgentSession._rebuildSystemPrompt` (`dist/core/agent-session.js`)
  собирает `_baseSystemPromptOptions`: `customPrompt` =
  `resourceLoader.getSystemPrompt()` (содержимое выбранного `SYSTEM.md`
  либо строка опции `systemPrompt`), `appendSystemPrompt` = склейка
  APPEND-источников, `contextFiles` = `resourceLoader.getAgentsFiles()`
  (зеркала), `skills` = `resourceLoader.getSkills()` (описания из
  frontmatter зеркал).
- `ExtensionRunner.emitBeforeAgentStart` (`extensions/runner.js`) отдаёт
  обработчику нормализованную копию (`normalizeBuildSystemPromptOptions`
  клонирует `contextFiles`/`skills`); мутации живут один ход, результат
  идёт в `_preparePromptAndToolLoadout` → дельта секций
  (`diffSystemPromptSections`).
- Развёрнутые промпт-шаблоны (`/имя аргументы`) получаются в
  `AgentSession.prompt`/`_queueUserInput` через `expandPromptTemplate`
  (`dist/core/prompt-templates.js`) и попадают **в пользовательское
  сообщение** (`event.prompt`), а не в системные секции; наша замена
  секций их не касается.
- Дети pi-subagents: `child-session.js` создаёт `DefaultResourceLoader` с
  явными `systemPrompt`/`appendSystemPrompt` (готовый эффективный промпт
  из `buildEffectiveSystemPrompt`), поэтому их `customPrompt`/`addendum` —
  производный текст; доставка заменяет секцию только при совпадении с
  нашим стартовым/применённым текстом и добавляет только пустые
  SYSTEM/APPEND-секции, чей источник pi — наше зеркало. Эксперимент из
  п. 3 подтверждает: производные строки не переписаны.

## Живые сценарии ручного прогона

Предусловия: зона D (миграция источников в `X.template`, имя пакета
`pi-template`, `/template` зоны C) и установленный pi-subagents; зеркала
до первого запуска отсутствуют.

1. **Старт сессии.** Запустить `pi` в проекте. Ожидание: на первом ходу в
   системном промпте есть глобальный/проектный контекст, описания скилов,
   SYSTEM/APPEND (доставка добавлением); рядом с источниками появились
   зеркала; сырых тегов `{{…}}` нет.
2. **`/reload`.** Править `AGENTS.md.template`, не применять: следующий ход
   видит прежний текст, статус «промпты отстали»; выполнить `/reload`.
   Ожидание: зеркало перезаписано на `session_shutdown`, новый рантайм
   видит новый текст, версии совпадают.
3. **Кнопка применения.** Сменить переменную в `/template` (зона C) — ход
   без изменений, статус «устарели»; нажать «обновить контекст». Ожидание:
   зеркала обновлены, следующий ход видит новый текст, версии совпали.
4. **Read тела скила.** Дать модели прочитать `SKILL.md` (зеркало), пока
   другая сессия/процесс держит своё зеркало. Ожидание: под локом зеркало
   приведено к варианту применённой версии этой сессии, лок снят на
   `tool_execution_end`.
5. **Спавн.** Вызвать `subagent` с агентом `foo` (и с `model` при
   необходимости). Ожидание: `agents/foo.md` отрендерен с параметрами
   спавна (`model@`/`level@` — из шапки/параметров), pi-subagents читает
   свежее зеркало; ребёнок получает расширение (тег `<active_agent>`,
   `@`-значения), каталог advertised показывает свежую шапку.
6. **Каталог advertised.** На `session_start` сессии-родителя каталог
   читается после/до нашего `session_start`; ожидание при нашем первом
   обработчике — свежие шапки; при обратном порядке — прошлое зеркало до
   следующего `session_start` (ограничение m1 дизайна).
7. **Порядок обработчиков у ребёнка.** Проверить, что замена секций
   path-расширения успевает до форса промпта inline-хуком pi-subagents:
   в промпте ребёнка контекст развёрнут, сырых тегов нет.

## Вопросы и решения (supervisor)

1. **Резолв `registerRequiredChildExtensions`** (git-пакет не резолвит
   bare-импорт — проверено экспериментом): решено — документированный
   экспорт через `createRequire.resolve` по npm-корням pi; прямой доступ к
   глобальному `Symbol`-реестру и зависимость в `package.json` отклонены.
2. **Составные вызовы `subagent`**: решено — обход аргументов без привязки
   к схеме (`{agent: …}`), параметры шага предварительными; имён нет —
   перерисовка всех агентских зеркал дефолтами.
3. **Перечень источников**: решено — перечень писателя форка плюс
   `.pi/agents` и legacy `.agents`, цепочка предков cwd вверх, зеркало
   только при наличии `X.template`; worktree-shadowing не воспроизводим.
4. **Пробел B.3 при отсутствующих зеркалах** (пи первый ход видел пустые
   секции — подтверждён живым прогоном): решено — правило «замена или
   добавление» (см. B.3); вариант «после первого запуска нужен `/reload`»
   отклонён как противоречащий принципу полноты.

## Остаточные риски и известные состояния

- **Порядок `session_start` с pi-subagents (m1)** на живом прогоне с обоими
  пакетами не проверялся: каталог advertised может отставать на один
  `session_start`; поведение не обходится и не маскируется.
- **Скобки `tool_call`/спавна** проверены юнит-сценариями и живой загрузкой,
  но не живым вызовом инструмента с подменённым провайдером: перехват
  read/спавна в реальном ходе — за ручным прогоном (сценарии 4–5).
- **Имя агента**: движок и `openSpawnBracket` сопоставляют агента по имени
  файла (`agents/foo.md` → `foo`); pi-subagents использует frontmatter
  `name`. При расхождении специфичные ключи `@<имя>`/цель спавна не
  совпадут: `@` действует, спавн перерисует все зеркала дефолтами (не
  ошибка, но без параметров). Конвенция «имя файла = имя агента» — из
  дизайна.
- **Вычисляемые переменные ребёнка** считаются один раз с предварительными
  `model`/`level` (после фикс-точки шапки не пересчитываются): значения
  команд, зависящих от `$model`/`$level`, в редком случае относятся к
  предварительной паре.
- **Стоимость старта**: рендер всех агентских файлов на `session_start`
  считает view каждого агента (shell-команды вычисляемых переменных, до
  5 с на команду); количество команд не замерялось.
- **win32**: ветки путей/лока под win32 не исполнялись (PLATFORM-ветки
  кода общие, разделители обрабатываются через `path`).
- **`package.json`** по-прежнему называется `roles` и указывает на
  `./index.ts` (имя — зона D); **`TESTING.md`** описывает старую ролевую
  механику (зона D).
- **Зона C не подключена**: методы API готовы, вызовы `/template`,
  записей `"var"` и статусной строки ещё нет; карта сессий живёт в
  замыкании `index.ts` — зоне C нужно будет взять из неё экземпляр.

## Правки по кросс-ревью (2026-10-16)

Диспозиция — `2_consumption/fixes.md` по `2_consumption/cross-review.md`;
baseline — коммит `400444f`. Изменены `session.ts`, `lock.ts`,
`agent.ts`, `render-set.ts`, `sources.ts`, `identity.ts`, `index.ts`,
`probe.mjs`; правки не закоммичены, ничего не застейджено. Пункты
1–12 применены; пункт 13 (принятое ограничение) зафиксирован.

### Major

**1. Опознание SYSTEM/APPEND.** Факт по коду pi: публичный
`getSystemPromptOptions()` есть только у `ExtensionCommandContext`
(`dist/core/extensions/types.d.ts:288`, `runner.js:729`), событийный
контекст его не даёт; форма источника (`systemPromptSource` загрузчика)
расширению вообще не видна — поле приватное (`resource-loader.d.ts`).
Поэтому фактически загруженный текст берётся из **первого
`before_agent_start`** до наших мутаций: `event.systemPromptOptions` — та
же нормализованная копия `_baseSystemPromptOptions`, что собрана
`_rebuildSystemPrompt` из кэша загрузчика (диск к этому моменту уже не
при чём). Правило `systemSection`:

- источник — проектный `.pi/…` при trust, иначе агентский (правила pi);
  источник не наше зеркало — не трогаем;
- пустая секция — добавление (как было);
- текст с тегом `<active_agent>` — производный промпт ребёнка, никогда;
- текст изменился после загрузки pi — мисс с громким предупреждением;
- ребёнок и текст без тега — источник файловый, замена (закрывает
  массовый случай гонки параллельных детей: pi прочитал X, наш старт
  записал Y, применённая Z — старое сравнение по X/Y молчало);
- не ребёнок — замена только опознанного текста (применённый, стартовый
  или текущий на диске); неопознанная строка (явный промпт SDK/CLI либо
  гонка) — без замены, с предупреждением. Строка SDK/CLI неотличима от
  файла в публичном API pi; выбран консервативный вариант «не заменять +
  предупреждать», мисс не молчит.

**2. Приоритет при спавне — как у потребителя.** `AgentFilePreliminary`
несёт флаги `explicitModel`/`explicitLevel`; цепочка: явный `model`
(вместе с суффиксом `:level`) → шапка YAML → дефолт сессии. Суффикс
уровня в выбранной модели сильнее `thinking`
(`resolveEffectiveThinking`), суффикс шапки разбирается
`splitThinkingSuffix`. При явном параметре фикс-точка шапки сходится за
один проход; `model@`/`level@` тела — фактические по той же цепочке.
Прогон: `subagent({agent:"foo", model:"p/q:high"})` при шапке
`model: x/y`, `thinking: low` рендерит тело `p/q/high` (раньше —
`x/y/low`).
