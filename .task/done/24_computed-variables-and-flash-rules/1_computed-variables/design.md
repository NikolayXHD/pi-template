# Вычислимые переменные pi-template: разбор и предложение

## 4.1. AS-IS: обзор механизмов

Объект правки — пакет `pi-template`
(`/home/kolia/.pi/agent/git/github.com/NikolayXHD/pi-template`), конфиг
`~/.pi/agent/template.json`, шаблоны контекста (`AGENTS.md.template`,
`roles/**`, `prompts/*.md.template`).

Переменные объявляются в `template.json`: `values` (статический список или
`{"shell": …}`), `initial` (строка, `{"shell": …}`, `{"env": …}`), `cwd`,
subagent-значения `@`/`@<name>`; `model`/`level` — неявные
(`IMPLICIT_VARIABLE_NAMES`, `parseVariableSpec`, vars.ts).

Вычисление view — `computeView` (vars.ts): shell-команды идут в порядке
объявления, окружение команды получает значения, известные к моменту запуска
(неявные переменные, сессионные переопределения, subagent-значения, статические
`initial`, env-lookup), плюс переменные, объявленные раньше. Переменная с
вычисляемым `initial` (shell/env) — read-only (`isComputedVariable`,
`readonlyProblem`).

Пересчёт вычисляемых значений: старт сессии и явные действия меню
(`buildView`, `recompute`, `recomputeAll`, session.ts). Смена модели или
уровня (`onModelChanged`, `checkActualModel`, session.ts) перерисовывает
текущую версию с новыми значениями `model`/`level`, но вычисляемые переменные
не пересчитывает: переменная, производная от `model`, устаревает ровно тогда,
когда её вход меняется. README это документирует («computed variables are
recomputed only by explicit menu actions»); design.md задачи 22 обещал пересчёт
каждый ход — реализация разошлась с дизайном.

Синтаксис шаблонов: условия `{{#if (eq v "x")}}`, `{{#if (in v "a" "b")}}`,
`{{#unless}}`, интерполяция `{{v}}`, partials, комментарии (`lintBlock`,
`lintCondition`, render.ts). Условие без вызова хелпера (`{{#if v}}`) — ошибка
линта («condition must be an eq or in call»). Литералы условия сверяются со
списком значений переменной (`literalWarning`).

Список flash-моделей захардкожен одним условием
`{{#if (in model "vllm/QUASAR-QAT/Qwen3.8-27B-QUASAR-NVFP4" "deepseek/deepseek-flash")}}`
в трёх файлах: `AGENTS.md.template` (правила «Не докладывай исполнение
протокола», «Не отчитывайся списком для галочки», «Словарь»),
`roles/snippets/tests.md.template` («Процесс резработки тестов»),
`prompts/teamlead.md.template` («Запрет на новые термины без согласования»).
Часть 2 задачи добавит в эти блоки новые правила — копировать список моделей
придётся в каждое новое место.

Три вещи делают заявку @NikolayXHD не покрытой существующими средствами:

1. shell-`initial` (`{"initial": {"shell": "…"}}`) умеет читать другие
   переменные из окружения, но вычисление через spawn — это таймаут 5 с,
   shell-синтаксис вместо условия и отсутствие сверки литералов;
2. пересчёт shell-значений только явный — переменная от `model` устаревает при
   смене модели;
3. шаблонный словарь (`eq`/`in` над переменной и литералами) не умеет давать
   условиям имена — список моделей повторяется текстом.

## 4.2. Предложение: поле `compute`

Переменная с полем `compute` — выражение-условие над другими переменными,
вычисляемое в процессе (без shell). Форма записи — синтаксис вызова
(решение 1 интервью).

```json
{
  "vars": {
    "is_flash": {
      "compute": "in model \"vllm/QUASAR-QAT/Qwen3.8-27B-QUASAR-NVFP4\" \"deepseek/deepseek-flash\""
    }
  }
}
```

Семантика:

- **Выражение** — выражение значения над переменными: строковый литерал —
  само значение; переменная — её значение; `concat e1 e2 …` — склейка
  литералов и переменных (как в именах partial'ов); условие (`eq`/`in` над
  переменной и литералами, `and`/`or`/`not`) — частный случай, порождающий
  `"true"`/`"false"`. Условие было исходной формой ограничения; требовать
  кейс строковой производной как цену за общность — неверно (@NikolayXHD):
  общая форма и есть механизм из постановки, узкая булева — случай без
  преимуществ.
- **Шаблоны получают те же связки** — `{{#if (or (in model "a") is_flash)}}`:
  условие становится одним языком в конфиге и шаблонах, а `or` закрывает
  пробел грамматики (сейчас составность выражается только вложением блоков).
  Имена `and`/`or`/`not`/`eq`/`in` запрещены для переменных — ошибка
  конфига.
- **Пересчёт** — при каждом построении view: старт, смена `model`/`level`,
  смена сессионной переменной, пересчёт из меню. Выражение чистое и дешёвое,
  поэтому пересчёт безусловный, в отличие от shell-команд. Это закрывает разрыв
  AS-IS: значение следует за входом, а не устаревает при смене модели.
- **Порядок объявления** — действует как для shell: выражение видит переменные,
  объявленные раньше, и неявные `model`/`level`. Ссылка на переменную позже —
  ошибка конфига (выражение разбирается, ссылки известны точно, не
  эвристикой по тексту команды).
- **`values`** — не объявляется рядом с `compute` (ошибка конфига); список
  значений переменной подразумеваемый `["false", "true"]` — он кормит lint
  литералов и допускает переменную в `statusVariable`.
- **`@`/`@<name>`** — прежняя семантика: строка заменяет вычисляемое значение
  (`"true"`/`"false"`). Без `@`-ключа дочерняя сессия вычисляет выражение в
  своём view (свои `model`/`level`) — flash-правила ребёнка следуют за моделью
  ребёнка.
- **Read-only / переопределение** — сессионное переопределение разрешено и
  побеждает вычисление (эксперименты с правилами flash-блоков);
  shell-вычисляемые остаются read-only. Домен булевой производной точен:
  вход или `@`-значение вне `{"true", "false"}` — ошибка, значение остаётся
  результатом выражения.
- **Ошибки** — неизвестная переменная в выражении, не-условие, ссылка на
  переменную позже: ошибка конфига. Деградация прежняя: сломанный
  `template.json` — view не строится, предупреждение с причиной.

**Отклонённые альтернативы:**

- shell-`initial` с `case "$model" in …` — механизм уже существует, но
  spawn вместо вычисления в процессе, только явный пересчёт (устаревание при
  смене модели), shell-синтаксис вместо условия, нет сверки литералов;
- именованный список значений (`in model flash_models`) — новая сущность
  (список) с единственным потребителем; выражение с литералами держит список в
  одном месте конфига, а второй потребитель появится — список выносится без
  изменения механизма;
- макрос условий (текстовая подстановка фрагмента условия) — собирает условие
  из кусков, ломает lint-модель «условие — один вызов над переменной».

## 4.3. Фолбэки

Значения по умолчанию для `is_flash` не вводятся: выражение либо вычисляется,
либо конфиг исправляется. Единственная деградация — существующая для сломанного
`template.json` (нет view — нет перерисовки, предупреждение с причиной);
fallback здесь маскировал бы ошибку конфига.

## 4.4. План реализации (черновик, уточняется после интервью)

- `vars.ts` — `VariableSpec.compute`; разбор выражения (обёртка
  `{{#if (…)}}{{/if}}` и проверка тем же кодом, что `lintCondition`);
  вычисление в `computeView` отдельной веткой (без shell, в порядке
  объявления); подразумеваемый `values`, ошибка `values` рядом с `compute`;
  `isComputedVariable` — по решению развилки 3.
- `render.ts` — условие-переменная в `lintBlock` (по решению развилки 2);
  lint литералов выражения — при разборе конфига.
- `session.ts` — пересчёт выражений входит в `buildView` и в смену неявных
  значений (`onModelChanged`, `checkActualModel`); shell-вычисление остаётся
  явным. Меню: для переменных на выражении убираются возраст и «пересчитать»
  (чистое вычисление), остаются для shell.
- `README.md`, сценарии `probe.mjs`: разбор `compute`, вычисление и порядок
  объявления, ошибки конфига, пересчёт при смене модели, условие-переменная в
  шаблоне, `@`-значения дочерних view.

Проверка: сценарии `probe.mjs` плюс ручной прогон в сессии — `is_flash` в
`template.json`, `{{#if is_flash}}` в шаблоне, смена модели → контекст stale →
применение → блок правил появляется/исчезает вслед за моделью.
