# Ревью 1: постановка против кода pi и pi-subagents

Ревьюер @pi-agent, 2026-10-12. Предмет — design.md против реального кода:
pi (extensions runner, system-prompt, конвейер промптов) и pi-subagents
(загрузка детей, наследование контекста, порядок расширений). Ранее прошли
раунды ревью качества изложения (issue.md, статус); этот раунд — о
реализуемости заявленных механизмов.

Вердикт: три находки (N1–N3) ломают заявленные инварианты дизайна, три (N4–N6)
— спекуляционные дыры. Общая картина: дизайн проверен против грамматики
Handlebars и собственного кода roles, но не против API точек перехвата pi и
механики детей pi-subagents.

## N1. «Throw, ход не начинается» нереализуемо в before_agent_start

Дизайн (раздел «Провал рендера»): контекстные файлы при провале без кэша —
throw, «ход не начинается»; кастомный промпт при провале — «блок с ошибкой
в UI».

Код: обработчик `before_agent_start` не может отменить ход.
`emitBeforeAgentStart` (src/core/extensions/runner.ts) оборачивает каждый
вызов обработчика в try/catch: throw превращается в отчёт об ошибке
расширения, цикл обработчиков продолжается, ход стартует. Тип результата
`BeforeAgentStartEventResult` содержит только `message` и `systemPrompt` —
поля блокировки нет. Throw из обработчика `input` гасится так же
(`emitInput`).

Следствие: при битом шаблоне в AGENTS.md новой сессии ход начнётся, и в промпт
уйдут сырые теги — инвариант «сырые теги модель не видит никогда» нарушается
ровно в худшем случае, на который политика рассчитана.

Альтернатива — гейт на input-событии. Обработчик `input` перед ходом
пре-рендерит входы хода (contextFiles, описания скилов, файл шаблона при
установленном происхождении, см. N3) с текущим view; при провале —
`ctx.ui.notify` с причиной, возврат отправленного текста в редактор через
`setEditorText`, ответ `action: "handled"`. Это реализуемая форма «ход не
начинается»: сообщение не уходит, пользователь правит шаблон и отправляет
повторно. Деградация в before_agent_start остаётся страховкой:
continuation-ходы (`turn_end` → `continue: true`) не проходят через
input-событие, и для них при провале применяется кэш, а без кэша — исключение
файла из contextFiles с предупреждением: файл не отдаётся, остальной промпт
корректен.

## N2. Рендер в субагент-процессах не работает как заявлено

Дизайн: «расширение рендерит и в субагент-процессах — иначе унаследованный
контекст дошёл бы до ребёнка сырыми тегами»; «хуки активны и в
субагент-процессах»; «файловые агенты pi-subagents грузят глобальный AGENTS.md
по умолчанию (`inheritGlobalContext ?? true`)».

Код, четыре факта.

1. Foreground-дети (subagent с `async: false`) — не отдельные процессы, а
   встроенные сессии в процессе родителя. Ambient-расширения из settings.json
   в них не грузятся: child-session.js строит загрузчик с
   `noExtensions: !launch.ambientExtensions`, а `ambientExtensions` истинен
   только для фонового раннера (child-launch.js, `host === "runner"`).
   Расширение в такой сессии отсутствует, ребёнок сам грузит контекстные
   файлы (`reviewer`: `inheritProjectContext: true`) — шаблонные теги уходят
   в промпт ребёнка сырыми. `PI_SUBAGENT_CHILD` в этом случае не установлена:
   её ставит только subagent-runner.js, процесс фоновых детей. Условие
   `{{#unless (eq PI_SUBAGENT_CHILD "1")}}` здесь не срабатывает — но и
   рендерить некому.
2. Фоновые дети: расширение грузится, но рендер через мутацию
   `systemPromptOptions.contextFiles` не действует. pi-subagents ставит свой
   prompt-runtime первым в списке расширений ребёнка
   (`prioritizeChildPromptRuntime`, child-session.js; комментарий в коде:
   prompt-runtime фильтрует контекст до того, как ambient-расширения увидят
   промпт ребёнка). Его обработчик `before_agent_start` возвращает
   `{ systemPrompt: переписанный }` — это устанавливает `forceSystemPrompt`
   (runner.ts), после чего `buildSystemPrompt` возвращает только форснутый
   текст (system-prompt.ts): мутации contextFiles более ни на что не влияют.
   Сырые теги доходят и сюда.
3. Утверждение о наследовании глобального AGENTS.md неверно. Для файловых
   агентов `inheritGlobalContext` по умолчанию false: agents.js читает его
   только из frontmatter (`=== "true"`), agent-management.js задаёт `false`
   встроенным. Выражение `?? true` в subagent-prompt-runtime.js — фолбэк
   рантайма на случай отсутствия ключа в конфиге запуска, а не дефолт
   файловых агентов.
4. Herdr-bridge-дети (pane-native) — полный pi-процесс с ambient-расширениями,
   но `PI_SUBAGENT_CHILD` в нём не установлена: скрывающее условие не
   собственный перехватчик промпта (herdr-pi-bridge.js) форсит systemPrompt по
   той же схеме, что и в пункте 2.

Следствие: заявленный механизм не доставляет рендер ни в один класс детей.
Инвариант «без сырых тегов» нарушается для любого ребёнка, наследующего
шаблонизированный контекст: глобальный AGENTS.md при явном
`inheritGlobalContext: true`, проектный AGENTS.md при
`inheritProjectContext: true` — это дефолт reviewer'а, стандартного агента
код-ревью в процессе пользователя.

Альтернатива.

- Рендер итогового текста: обработчик рендерит `event.systemPrompt` и
  возвращает `{ systemPrompt: отрендеренный }`. Работает при любом порядке
  обработчиков: если pi-subagents уже форснул промпт — рендерится форснутый
  текст; рендер идемпотентен для уже отрендеренного содержимого. Закрывает
  фоновых детей и herdr-bridge. Цена: политика провала становится
  промпт-гранулярной, а не файловой — для детей допустимо: кэш последнего
  успеха на весь промпт ребёнка.
- Foreground-дети расширением не лечатся: сессия без наших хуков. Вариант —
  честно зафиксировать ограничение в дизайне и перенести PR в pi-subagents из
  раздела «Что не в этой итерации» в обязательный шаг (встроенный рендер-хук
  или гарантия ambient-загрузки в детях). До PR — в репозиториях с
  шаблонизированным проектным AGENTS.md отключать `inheritProjectContext` у
  детей или не шаблонизировать проектный AGENTS.md.

## N3. Рендер `event.prompt` — не та точка перехвата

Дизайн (план реализации): «рендер `event.prompt` — текста пользовательского
сообщения после подстановки `$1`-аргументов pi».

Код: в `before_agent_start` поле `prompt` — уже развёрнутый текст без признака
происхождения: расширение шаблонов происходит в `prompt()` до хука
(agent-session.ts). Текст пользовательского сообщения и развёрнутый шаблон
неразличимы. Установленный у пользователя pi-prompt-template-model
перехватывает шаблоны со своим frontmatter собственными командами: команды
расширений диспетчеризуются раньше input-события, текст уходит через
`sendUserMessage` с source `"extension"`.

Следствие: рендер всего `event.prompt` обрабатывает произвольный текст
пользователя. Вопрос про `{{ }}`, вставленный код или логи с mustache-подобным
синтаксисом либо исказятся рендером, либо по политике «блок вызова» не
пройдут — обычное сообщение пользователя блокируется.

Альтернатива — происхождение (provenance) на input-событии: обработчик
запоминает «последний ввод — `/name …`, где name — известный файл шаблона», и
`before_agent_start` рендерит `event.prompt` только при совпадении.
Непровенансированный текст не рендерится никогда. Проверку провала шаблона
вынести в гейт input-события (механизм N1): пре-рендер файла шаблона с текущим
view, при провале — причина в UI и возврат текста в редактор. Ограничение:
шаблоны под управлением pi-prompt-template-model (с его frontmatter)
рендериться переменными не будут — либо зафиксировать как ограничение, либо
согласовать порядок с этим расширением.

## N4. Подстановка переменных в shell-команды — инъекция

Дизайн (раздел «Конфиг»): «ссылки на другие переменные в shell-командах
подставляются до запуска; delimiter не конфликтует с `${}` самого shell (форма
уточняется при реализации)».

Значения переменных приходят из мира: имена git-веток — произвольные строки в
клонированном репозитории, имена файлов — тоже. Строковая подстановка такого
значения в тело команды — shell-инъекция: ветка с именем `x; rm …` в чужом
репозитории исполняется при вычислении зависимой переменной. Не специфицированы
и циклы ссылок (a → b → a) с порядком вычисления.

Альтернатива: передавать значения через окружение команды, а не текстовой
подстановкой — процесс запускается с `PI_VAR_<name>=<значение>`, команда
ссылается на `$PI_VAR_role`. Инъекция исчезает, вопрос делимитера снимается
сам. Циклы ссылок — ошибка конфига при загрузке; порядок вычисления —
топологический.

## N5. Две зоны выполнения команд: agent dir против проекта

Дизайн: «shell-команды выполняются в каталоге agent dir» — и тут же пример
`git_branch: {"current": {"shell": "git rev-parse --abbrev-ref HEAD"}}`.

Противоречие: в agent dir команда вернёт ветку репозитория агента, а не
проекта. Состояние мира — атрибут проекта: cwd сессии, у детей — их
собственный cwd (worktree).

Альтернатива: per-var поле `"cwd": "agent" | "project"` в схеме конфига
(дефолт — agent, как сейчас; для переменных мира — project). Для детей
переменная с `cwd: "project"` вычисляется в их собственном cwd.

## N6. Корни шаблонизации и ключи реестра партиалов не перечислены

Дизайн: инвариант «файлы вне шаблонизируемых корней не трогаются»; партиалы —
«имя — путь от корня agent dir»; материализация — «путь от корня agent dir».

Корни перечислены классами ресурсов (AGENTS.md, скилы, промпты), а не путями.
Следствия:

- package-скиллы и промпты — сторонний контент; скилл про шаблоны с легитимным
  `{{ }}` в тексте попадает под рендер: линт валит файл, описание скила
  выпадает из промпта, тело даёт ошибку read;
- путь от корня agent dir не адресует проектные файлы, которые в scope:
  проектный AGENTS.md, `.pi/skills`, `.pi/prompts`;
- коллизия ключей реестра: глобальный `skills/foo/SKILL.md` и проектный с тем
  же относительным путём.

Альтернатива: точный список корней — agent dir (AGENTS.md, `roles/`,
`skills/`, `prompts/`) и проектные (цепочка AGENTS.md от cwd вверх,
`.pi/skills`, `.pi/prompts`); package-ресурсы исключены из рендера. Ключи
реестра и пути материализации — с префиксом корня: `agent/roles/preflight.md`,
`project/AGENTS.md`.

## Мелочи

- Миграция в двух местах дизайна даёт разные формы включения роли: простая
  строка `{{> (concat …)}}` в разделе «План реализации» против условия
  `PI_SUBAGENT_CHILD` в разделе «Конфиг». Синхронизировать после решения по N2.
- probe.mjs не содержит сценариев динамических партиалов, на которые ссылается
  раздел «Роль — динамический партиал» («механизм проверен на живом движке»);
  `concat` отсутствует в `knownHelpers` текущего render.ts. План переписи
  render.ts это покрывает, но ссылка на probe сейчас опережает код.
- Статусная строка «все переменные сессии» при росте их числа переполнит футер;
  показывать только сессионные переопределения.
- Перехват read: при замене `content` надо согласованно менять
  `structuredContent` и `details` — контракт `tool_result` в документации pi.
