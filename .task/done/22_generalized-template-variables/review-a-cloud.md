# Кросс-ревью пакета A «ядро шаблонизатора» (cloud)

Объект: рабочее дерево `/home/kolia/git/pi`, незакоммиченные правки:
`packages/coding-agent/src/core/templates/{vars,render,context-dir}.ts`,
`packages/coding-agent/test/templates-{vars,render,context-dir}.test.ts`,
дифф `packages/coding-agent/package.json` и трёх локфайлов.

Сверка велась с design.md (разделы «Переменные и view», «Контекстная
директория», «Линт», «Провал рендера») и spec-a-engine.md, с учётом уточнений
ведущего из постановки. Режим — только чтение, правок нет.

Метод: чтение файлов целиком с диапазонами; поиск — `git grep -in --untracked`;
поведение модулей и разбор Handlebars проверялись точечными запусками Node по
уже установленным модулям (в режиме read-only, без правок репозитория). Тесты и
`npm run check` в аудиторском режиме не запускались.

## Находки

### F1 — critical — render.ts:263

Объявленная переменная без списка значений считается необъявленной в
интерполяции и в первом аргументе `eq`/`in`.

```ts
if (!(IMPLICIT_VARIABLES as readonly string[]).includes(name) && context.variables[name] === undefined) {
	issues.errors.push(`${what}: переменная "${name}" не объявлена`);
```

`LintContext.variables` (render.ts:38-42) определяет `undefined` как «списка
нет» (переменная объявлена), а не как «не объявлена». Проверка выше этого не
различает: для `{ free: undefined }` вызовы `lintTemplate("{{free}}")` и
`lintTemplate('{{#if (eq free "x")}}...')` дают
`интерполяция: переменная "free" не объявлена` /
`первый аргумент условия: переменная "free" не объявлена` (проверено запуском).

Расхождение с design.md: «переменная без списка значений: сравнение литералов
не проверяется, динамический партиал по ней — ошибка (резолвить нечем)» и
«Пути-переменные — любые объявленные переменные» (spec-a). Интерполяция и
`eq`/`in` по такой переменной обязаны быть легальны. Это не экзотика: в
примере конфига design.md ровно такая переменная — `git_branch`
(`current` без `values`). То есть пример из дизайна нельзя использовать в
шаблоне, а линт отправит его в манифест как ошибку; для контекстного файла это
по «Провалу рендера» означает отказ стартовать.

Код внутренне противоречив: в `lintDynamicPartial` та же развилка сделана
правильно — `Object.hasOwn(context.variables, path.parts[0])`
(render.ts:359-362), а «списка нет» проверяется отдельно как
`=== undefined` (render.ts:377-383). Значит, для одной и той же переменной без
списка динамический партиал даёт «нет списка — резолвить нечем», а интерполяция
— «не объявлена».

Проверено сквозным запуском `writeContextDir`: `AGENTS.md` с текстом
`declared free: {{free}}` и `values = {}` (а также
`values = { free: undefined }`) получает в манифест
`линт: интерполяция: переменная "free" не объявлена`, и файл в зеркало не
пишется.

Тесты: `templates-render.test.ts:96,119-120` используют `free: undefined`
только как отказ динамического партиала; легальных кейсов `{{free}}` /
`(eq free ...)` нет, в `templates-context-dir.test.ts` у всех переменных есть
`values`. Если ведущий имел в виду, что переменная без списка значений —
ошибка и в сравнениях, то это противоречит design.md и его нужно править;
текущий код не согласован ни с одной из двух формулировок.

### F2 — major — vars.ts:123-127, 163-172, 204-205

Сессионное переопределение, переданное в `implicit`, затирается `current`
переменной и не попадает ни в view, ни в окружение shell-команд.

Документация самого модуля (vars.ts:124-127): «Значения, известные без
вычисления: неявные `model`/`level`/`PI_SUBAGENT_CHILD`, сессионные
переопределения». Дальше код безусловно перекрывает их машинным значением:

- статический `current`: `known[name] = current; view[name] = current;`
  (vars.ts:167-168);
- `{"env": …}`:
  `known[name] = envBase[current.env] ?? ""; view[name] = known[name];`
  (vars.ts:170-171);
- shell `current`: в цикле вычисления
  `view[name] = value; known[name] = value;` (vars.ts:204-205).

Проверено запуском: при `implicit = { role: "dev" }` и
`role: { values: ["a","b"], current: "preflight" }` в отчёте
`view.role === "preflight"`; то же для `{"env": …}` и shell `current`.

Расхождение с design.md: view — «машинные значения, сессионные
переопределения…»; resume — «последнее значение каждой переменной по её
записям сверх машинных значений конфига»; окружение команды — «неявные
переменные, статический `current` и сессионные переопределения (независимо от
позиции объявления)». Если `implicit` — единственный вход для невычисляемых
значений, то через текущий API требование «переопределение в окружении
команды» невыполнимо: переопределение не может одновременно победить в view и
остаться в окружении. Пострадают `role` (пример миграции: `current` =
`preflight`), `vllm` и любая переменная с `current`, то есть весь смысл `/var`.

Тесты: `templates-vars.test.ts` подаёт в `implicit` только `model` (или
ничего); кейса «переопределение побеждает `current`» нет. Нужно решение
ведущего: либо `implicit` перекрывает `current` (и это фиксируется тестом),
либо контракт `implicit` сужается до трёх неявных имён, а способ передачи
переопределений (и их попадание в окружение) описывается отдельно.

### F3 — major — render.ts:293-318, context-dir.ts:112-133

Статические партиалы проектного корня (имена с префиксом `.pi/`) не работают:
Handlebars не разбирает имя, начинающееся с точки.

`lintTemplate("{{> .pi/prompts/p.md}}")` возвращает
`шаблон не разбирается: Parse error … got 'SEP'`; `renderTemplate` бросает то
же (проверено на установленной версии handlebars 4.7.10). При этом регистр
партиалов кладёт проектные файлы именно под именами `.pi/skills/...`,
`.pi/prompts/...` (context-dir.ts:129-131; тесты
`templates-context-dir.test.ts:139,151`), а design.md определяет партиал как
«файл, подключаемый тегом `{{> имя}}`; имя — путь от корня своего каталога…
проектные — с префиксом `.pi/`». Легальная форма «партиалы статические» и
правило «статический партиал — существование файла» для проектного корня
недостижимы: до проверки существования дело не доходит, ошибка парсера сырая.
Единственная работающая форма — `{{> (concat ".pi/prompts/p.md")}}`
(проверено), но это динамическая форма, и она не покрыта тестами для `.pi/`.
Проверка `pi/prompts/p.md` без точки даёт «партиал не найден», то есть
зарегистрированное имя недостижимо статически в любом написании.

Если проектные партиалы задумывались только динамическими, это нужно
зафиксировать в словаре и в сообщении линта (сейчас пользователь получает
ошибку парсера), а тест «именование партиалов обоих корней» — расширить.

### F4 — minor — context-dir.ts:127

Проверка одноимённости партиалов вопреки снятому правилу.

```ts
if (partials.has(name)) throw new Error(`партиал "${name}" зарегистрирован из двух корней`);
```

Уточнение ведущего: «проверки одноимённости нет»; interview §15 N6:
«уникальность по построению — правило одноимённости снято». При текущих корнях
коллизия недостижима (пространства имён не пересекаются), то есть это мёртвая
защита, к тому же бросающая исключение и обрывающая весь `writeContextDir`, а
не попадающая в манифест. Ожидаемо: проверку убрать либо свести к проблеме
отчёта.

### F5 — minor — context-dir.ts:236,257 + utils/frontmatter.ts:17-21

Дыра в YAML-защите: незакрытый frontmatter принимается молча.

`validateFrontmatter` опирается на `parseFrontmatter` форка, а тот при тексте,
начинающемся с `---` без закрывающего `\n---`, возвращает `{frontmatter: {}}`
без исключения (проверено: `parseFrontmatter("---\nname: x\nbody")` не
бросает). Значит, отрендеренный файл, у которого потерялся закрывающий `---`
(например, условие съело строку), записывается в зеркало, frontmatter исчезает
вместе с описанием скила, а «сбой валидации — провал рендера файла» не
срабатывает. Тест покрывает только закрытый, но невалидный YAML (`badyaml.md`).
Нужен либо явный контроль закрывающего разделителя, либо зафиксированное
ограничение.

### F6 — minor — context-dir.ts:199-249

Зеркало не чистится от исчезнувших источников.

Если источник пропал (удалён скил/промпт/AGENTS.md), прежний файл зеркала
остаётся, а манифест и `variables.json` на него уже не ссылаются. Соответствие
1 к 1 (design.md: «соответствие 1 к 1 источникам») нарушается в обратную
сторону; если пакет B перечисляет ресурсы по зеркалу, а не по манифесту,
удалённый скил/промпт может остаться видимым. В spec-a чистка не описана —
нужно решение: чистить или зафиксировать сохранение.

### F7 — minor — vars.ts:133-137, 156, 186-206 ↔ context-dir.ts:63

`ViewReport.values` не содержит ключей для объявленных переменных без списка —
при передаче в `writeContextDir` теряется признак «объявлена».

`values[name]` появляется только при статическом списке или успешном shell
`values`; у переменной без `values` (пример `git_branch`) и у переменной с
упавшим shell-списком ключа нет. Но `ContextDirOptions.values` документирован
как «имя переменной → список или `undefined`» (context-dir.ts:62-63), а
`LintContext` (render.ts:38-42) требует именно записи со значением `undefined`,
чтобы отличить «списка нет» от «не объявлена» через `Object.hasOwn`. Даже
после исправления F1 признак потеряется на стыке модулей пакета A: сквозной
прогон с `values = {}` даёт «не объявлена». Либо `computeView` добавляет
`undefined` для каждой объявленной переменной, либо `writeContextDir` строит
реестр переменных не из `values`, а из полного набора имён конфига.

### F8 — minor — context-dir.ts:79-81, 88-108

Путь зеркала не выдерживает win32 и относительных каталогов.

`mirrorRelativePath` срезает только ведущий `/`. На win32 абсолютный источник
начинается с буквы диска, и зеркальный путь получает `:` и `\` — как имя файла
это не создаётся (`cmd.exe /c` в этом же пакете заявлен, то есть платформа
подразумевается). При относительном `agentDir`/`projectDir` с `..` зеркальные
пути уходят выше `contextDir` (для `SYSTEM.md`/`APPEND_SYSTEM.md`/скилов код
берёт каталог как передан). Формулировка design.md («абсолютный путь источника
без ведущего разделителя») сама про win32 молчит — это скорее тема решения
ведущего, но реализация буквально наследует проблему.

## Сверено и совпало

- Контракт shell: `sh -c` / `cmd.exe /c` (vars.ts:222-223), фиксированный
  таймаут 5 с, `SIGKILL` (vars.ts:230-237), stdout построчно, trim, пустые
  игнорируются, дубликаты схлопываются (vars.ts:254-265), первая строка для
  `current` — соответствует design/spec, покрыто тестами.
- Ненулевой exit/ошибка — переменная без списка/значения и сообщение в
  `problems` (vars.ts:186-203); кэш/безопасность не страдают.
- Окружение команды без переопределений: окружение процесса + неявные +
  статический `current` и `{"env": …}` любой позиции + вычисленные ранее;
  собственное значение команде не видно (vars.ts:163-181); подтверждено
  `templates-vars.test.ts:260-290`.
- Порядок вычисления — порядок объявления, повторных вычислений нет;
  упоминание более поздней вычисляемой переменной — предупреждение с
  дедупликацией; имена вне view не трогаются (vars.ts:207-209,347-403).
- `{"env": …}`: сырое значение процесса, отсутствие — пустая строка, без exec;
  shell и env `current` — read-only (`isComputedVariable`, vars.ts:74-78).
- Разбор конфига: строгие ключи, формы `values`/`current`/`cwd`, запрет
  неявных имён, проверка идентификатора, коллизия с окружением — ошибка
  (vars.ts:95-140,305-360; тесты).
- Каноническая сериализация: стабильный порядок ключей, массивы сохраняют
  порядок, применяется к `variables.json` (vars.ts:377-393; context-dir.ts:252;
  точная строка в тесте).
- Грамматика и линт: блоки `if`/`unless` над `eq`/`in` с переменной первым
  аргументом и строковыми литералами, строгое `eq`, вырезание options у `in`,
  `concat`, комментарии; таблица отказов совпадает с design (render.ts:103-260;
  тесты).
- Рендер: свой environment, `knownHelpersOnly`, `knownHelpers` = eq/in/concat/
  if/unless, `noEscape: true`; отсутствие партиала — исключение
  (render.ts:80-99; тесты). `{{else if …}}` разбирается и рендерится верно
  (проверено).
- Frontmatter рендерится наравне с телом, отдельной ветки нет (тест
  `renderTemplate`).
- Регистр партиалов: агент — `roles/**`, `skills/**`, `prompts/**`; проект —
  `.pi/skills/**`, `.pi/prompts/**`; имена от корня своего каталога;
  файлы-входы не регистрируются (context-dir.ts:112-133; тесты).
- Перечень источников: каталог агента + цепочка проекта через
  `loadProjectContextFiles` форка, приоритет имён и worktree-механика не
  переизобретены (context-dir.ts:88-108; resource-loader.ts:119-163);
  `roles/**` в зеркало не входит.
- Зеркало: абсолютный путь минус ведущий разделитель, `*.md` рендерятся,
  остальное — симлинки на источники; манифест «источник → файл + ошибки»;
  `variables.json` канонический; атомарная запись временным именем,
  неизменившееся не переписывается; при провале рендера прежнее содержимое
  сохраняется (context-dir.ts:199-253,266-299; тесты).
- YAML-валидация закрытого frontmatter: невалидный YAML — ошибка в манифест,
  файл не пишется (тест `badyaml.md`).
- `THINKING_LEVELS` совпадает с фактическим набором уровней форка
  (cli/args.ts:60).
- Зависимость: `handlebars` запинен точно `4.7.10` (package.json:61), это
  актуальная версия npm (`npm view handlebars version` → 4.7.10), integrity в
  трёх локфайлах совпадает с npm (`sha512-P5VJ…Kg==`); среди новых зависимостей
  нет install-скриптов (`prepack` у minimist — не install), запись allowlist в
  `scripts/generate-coding-agent-shrinkwrap.mjs` не требуется; локфайлы
  согласованы (root-lock: у minimist снят `dev`, добавлены neo-async,
  source-map, wordwrap, uglify-js).
- Качество кода: erasable TS, без `any`, без inline-imports, без `enum`/
  `namespace`, доки не противоречат коду (кроме F2 и оговорки F11).
- Терминология: новых доменных имён вне словаря design.md не найдено;
  сообщения линта используют словарь дизайна («машинное значение», «список
  значений», «неявная», «партиал»).
