### 2. Точка вставки роли — декларативная, в пользовательском файле (@NikolayXHD)

Дописывание в конец отклонено: это новая сущность без необходимости.
Пользователь вписывает диспетчер партиалом куда хочет (например,
`{{> role.md}}` в глобальном AGENTS.md). Расширение ничего не
дописывает. Потеря возможности линтинга включения диспетчера принята
как цена декларативности. Дизайн обязан: провал рендера файла не
пропускает сырые теги в промпт — правило «текст прошлого успеха»
обобщается в per-file кэш последнего успешного рендера. Resume
становится восстановлением переменных, а не текста роли.

### 1. Механизм растворения роли — диспетчер-шаблон (@NikolayXHD)

Выбран диспетчер: один файл `{{#if (eq role "x")}}{{> x.md}}{{/if}}…`,
расширение не знает имён ролей. Роль без ветки диспетчера — ловится
линтом по конфигу. Из кода уходят `roleNames`, проверка «роль найдена»,
загрузка файла роли по имени.

### 3. Тела скилов — рендер при чтении (@NikolayXHD)

Шаблонизатор «только для описаний» отклонён как бессмысленный: тела
скилов рендерятся перехватом результата read. Инвариант: рендер
применяется только к объявленным шаблонизируемым корням (ресурсы agent
dir), произвольные файлы проекта с `{{ }}` внутри не трогаются.

### 4. Промпты агентов — материализация `.md.template` → `.md` (@NikolayXHD)

> Пересмотрено позже (см. §7 и design.md): схема отклонена как
> непрактичная на этом этапе, агенты не шаблонизируются.

- Шаблон: `agents/<name>.md.template`; скан pi-subagents грузит
  только файлы, кончающиеся на `.md`, суффикс он не видит.
- На попытке старта агента (tool_call инструмента pi-subagents)
  расширение рендерит шаблон и атомарно пишет `agents/<name>.md`.
  Discovery pi-subagents кэшируется с отпечатком (mtime+size) и
  перечитывает файл при изменении; родитель строит промпт в памяти
  и передаёт ребёнку, ребёнок файл не читает (проверено по
  effective-system-prompt.js / child-launch.js).
- Переменные шаблонов агентов: машинные и сессионные.
- Гонка межсессийных записей: файловый лок от рендера до события
  старта ребёнка (`subagent:child-status` started,
  `subagent:async-started`, `subagent.nested.started`); lease-таймаут
  как страховка освобождения.
- Остаточные риски, приняты @NikolayXHD: читатели вне протокола
  (herdr-мост, doctor, slash-листинги, рекламные блоки) читают
  последнюю чужую запись; вложенные (внучатые) спавны рендерятся по
  машинным значениям — сессионные переменные родителя в дочерние
  процессы не попадают. Если механизм приживётся — PR в pi-subagents
  для встроенной интеграции.
- Моё предложение «только машинные переменные, enforced линтом» —
  отклонено.

### 5. Конфиг и UI (@NikolayXHD)

> Пересмотрено позже (см. design.md): вычисляемое `current` — раз в
> ход с заморозкой view, а не «на каждом рендере»; меню показывает
> только переопределяемые переменные.

- Расширение переименовывается под фокус на шаблонах: pi-handlebars;
  конфиг — handlebars.json (имя следует за расширением).
- `cycle` убран полностью; Ctrl+R умирает вместе с ним.
- `values`: статический список или `{"shell": "..."}`. Контракт shell:
  значения — строки stdout, по одной на строку, trim, пустые
  игнорируются, дубликаты схлопываются; ненулевой exit или таймаут —
  предупреждение, переменная без списка; вычисление при старте сессии
  и на обновлении снапшота.
- Вычисляемые значения: `"current": {"shell": "..."}` — read-only,
  машинная, вычисляется на каждом рендере, сессионное переопределение
  запрещено, меню не показывает; ссылки на переменные подставляются
  перед запуском (delimiter — на дизайн, без конфликта с shell-`${}`).
- Ограничение: значения — строки для сравнения; контент через
  значения не проводится — интерполяция Handlebars не рекурсивна,
  роли сами являются шаблонами.
- UI: `/var` (меню всех переменных), `/var <имя>` (меню значений),
  `/var <имя> <значение>` (прямая установка); `/role` не сохраняется.
  Статусная строка показывает все переменные сессии компактно.

### 6. Роль — динамический партиал вместо диспетчера (@NikolayXHD)

> Форма имени уточнена позже в design.md: значения — имена файлов без
> расширения, партиалы регистрируются полными путями —
> `{{> (concat "roles/" role ".md")}}`.

`{{> (concat "role_" role)}}` — основной механизм роли; диспетчер
if/elif остаётся легальной, но не рекомендуемой формой. Линт
резолвит имя партиала по конечной области значений; материализация
видит упоминание `role`. В связке со shell-values добавление роли =
создание файла, без правок конфига и диспетчера. Проверено на живом
движке: партиал рендерится с текущим view.

### 7. Откат шаблонизации агентов (@NikolayXHD)

Материализация `.md.template` → `.md` с локом признана непрактичной
на этом этапе. `agents/*.md` — простой markdown, вне шаблонизируемых
корней. Условность доходит до субагентов по наследству: дети грузят
глобальный AGENTS.md (по умолчанию) и проектный
(`inheritProjectContext: true`), расширение рендерит его и в
субагент-процессах. Сессионные переопределения в детей не идут —
ребёнок рендерит машинным view. Правило ролей «не активироваться в
субагент-процессах» умирает.

### 8. Провал рендера — кэш последнего успеха возвращён (@NikolayXHD)

Мой ход с «сырыми тегами при провале» (@pi-agent) отклонён: видимость
ошибки создаёт предупреждение, сырые теги в промпте не добавляют
ничего, кроме мусора модели. Итог: файл либо отрендерен корректно,
либо не отдаётся вовсе. С кэшем — последний успешный рендер; без кэша
(свежая сессия) — throw для контекстных файлов, ошибка инструмента
для тел скилов, блок вызова для промптов.

### 9. Провал рендера описания скила (@NikolayXHD)

Скил с несрендеренным описанием не попадает в список промпта,
ход продолжается; тело остаётся читаемым, вызов по имени работает.
Подтверждено после разбора: несоизмеримость ущерба с AGENTS.md.

### 10. Факты из env — через вычисляемую переменную (@NikolayXHD)

Прямой доступ шаблонов к env отклонён: второй канал мира мимо конфига, линта и
хеша. Паттерн — переменная с именем, совпадающим с env-переменной:
`PI_SUBAGENT_CHILD` со значениями ["", "1"] и `current` через
`{"env": "PI_SUBAGENT_CHILD"}` (lookup без exec; алиас не вводится,
нормализация значений не нужна — приняты сырые @NikolayXHD); дети вычисляют её
сами. Скрытие ролей от субагентов — шаблонное условие
`{{#unless (eq PI_SUBAGENT_CHILD "1")}}…`, а не зашитое правило кода. Моё
предложение встроить неявную переменную `process` — отклонено как излишнее:
механизм вычисляемых переменных уже покрывает кейс. Форма `{"env": "VAR"}` для
`current` добавлена в схему конфига наряду со shell.

### 11. Гейт на input-событии (@NikolayXHD)

Принят гейт: обработчик input-события перед ходом пре-рендерит входы хода
(contextFiles, описания скилов, файл шаблона при известном происхождении);
при провале — причина в UI, отправленный текст возвращается в редактор
через `setEditorText`, ответ `action: "handled"` — сообщение не уходит,
ход не стартует. В before_agent_start остаётся страховка-деградация для
continuation-ходов (без input-события): кэш последнего успеха, иначе
исключение файла из contextFiles с предупреждением. Раздел «Провал рендера»
design.md переписывается под механизм: «throw, ход не начинается» меняется
на гейт.

### 12. Дети — обязательное расширение через host-реестр (@NikolayXHD)

Принят механизм `registerRequiredChildExtensions` (документированный
хост-API pi-subagents, docs/agents.md «Required host extensions»): при
`session_start` расширение регистрирует себя host-required для `sessionId`
сессии — импорт из `pi-subagents/required-child-extensions`, зависимость
пакета. Путь — та же точка входа `index.ts`, что в манифесте пакета
(один экземпляр в background-детях).

Strict: `requireForAllRunners: true` — запуски, не способные грузить
pi-расширения (внешние CLI-агенты, machine-размещения), отвергаются
до старта: ребёнок либо рендерит, либо не запускается.

Рендер в ребёнке: при установленном `forceSystemPrompt` (более ранний
обработчик — prompt-runtime, bridge) — рендер итогового `event.systemPrompt`
и возврат `{systemPrompt}`; иначе — правка contextFiles и описаний скилов
в `systemPromptOptions`. Порядок обработчиков не важен. `session_start`
в детях без throw: ошибки конфига — предупреждения, throw в фазе биндинга
ребёнка = отказ запуска.

Отклонены: `subagentOnlyExtensions` по агентам (дисциплина), PR в
pi-subagents до обкатки, срез scope до ресурсов agent dir — проектный
AGENTS.md остаётся шаблонизируемым.

### 13. Архитектура — правки pi: переопределение директорий контекста (@NikolayXHD)

Бесправковые компромиссы (обёртка в PATH, env-редирект с симлинками,
перехват итогового промпта, перехват read) отклонены как грязные.
Принято:

- форк pi, локальный клон уже есть; правки идут в ветку personal,
  всегда поверх последнего релизного тега;
- при локальной сборке учитывать ограничения российского IP
  (для информации);
- правка хирургическая: pi получает возможность переопределить обе
  директории источников контекста — каталог агента и каталог проекта
  (цепочка контекстных файлов, `.pi/*`); state (auth, sessions,
  settings, models) читается из настоящего agent dir, тень несёт
  только текстовые ресурсы;
- структура теневой контекстной директории проектируется под цепочку
  AGENTS.md, включая файлы вне директории проекта (предки cwd);
- расширение pi-handlebars работает в модифицированном pi и пользуется
  переопределением: рендерит тень под текущий view, перенаправляет pi
  на неё, перезагружает ресурсы.

Следствия для прежних решений:

- обёртка запуска не нужна;
- решение 11 (гейт на input-событии) умирает: провал рендера = тень не
  обновилась, pi читает прежнее содержимое (кэш по построению),
  предупреждение называет файл; нового файла в тени нет — pi его
  просто не видит;
- решение 12 (registerRequiredChildExtensions) остаётся для
  foreground-детей: расширение там не грузится ambient и должно
  попасть в сессию ребёнка, чтобы переопределить каталоги её view;
- фоновые раннеры и herdr-дети: расширение грузится в них само
  (ambient) и делает ту же работу в своём session_start — наследование
  не нужно.

Открытые точки дизайна: форма переопределения (API расширения, env
или флаг запуска), представление цепочки предков cwd в тени, первая
загрузка до session_start расширения (грузится из настоящего каталога,
переключается на тень до первого хода).

### 14. Без расширения — весь механизм в форке (@NikolayXHD)

Расширения-пакета не будет: раз всё равно платим правками кода, логика
живёт в самом форке. На этом этапе — осознанный выбор «пока что».

Следствия:

- решение 12 (registerRequiredChildExtensions) умирает полностью:
  все дочерние сессии — это тот же модифицированный pi (встроенные
  foreground — тот же процесс, фоновые раннеры — тот же бинарник,
  herdr — pi из PATH машины), рендер встроен и работает везде без
  вопроса «кто грузится в ребёнке»;
- открытая точка «форма переопределения» из решения 13 сужается:
  не публичный API расширения, а внутренняя механика форка —
  модуль рендера тени + подмена каталогов в точках загрузки ресурсов;
- первая загрузка упрощается: форк вычисляет view и рендерит тень ДО
  начальной загрузки ресурсов (машинные значения из handlebars.json,
  сессионные переопределения и модель — из записи сессии на resume);
  танец «стартовать с настоящего каталога, переключиться до первого
  хода» не нужен;
- смена переменной или модели: перерисовка тени + перезагрузка
  ресурсов из неё — нативно в форке;
- пакета, манифеста, entry в settings.json, probe.mjs рядом с пакетом
  нет — тесты едут в тестовую инфраструктуру форка.

Цена: поверхность ребейза personal на релизные теги растёт — правки
затрагивают config, resource-loader, регистрацию команды /var,
статусную строку, записи сессии; при апстриме это всё равно пришлось
бы согласовывать. При живом кейсе выделения в расширение — вернуться.

### 16. Разворот архитектуры: X.template, узкие локи, расширение (@NikolayXHD)

Принято (обсуждено и закрыто, пересмотру не подлежит):

- источники — файлы `X.template` в каталоге агента и в проекте; pi их не
  видит (кандидаты контекста — точные имена, скилл-корень — по
  `SKILL.md`, промпты — `.md`-дети);
- рядом с шаблоном генерируется `X` по общему для всех сессий пути;
- точки потребления рендерят под узким локом единообразно: проверка
  свежести — рендер под view сессии, запись, чтение, отдать. Лок
  покрывает ВСЕ чтения шаблонизируемых файлов: и загрузку pi
  (AGENTS.md цепочки, SYSTEM/APPEND, промпты, frontmatter скиллов), и
  чтение тел скилов read tool'ом. Специальный путь «read tool отдаёт из
  памяти без лока» отклонён: frontmatter скила идёт мимо read tool,
  частичное покрытие не оправдывает второго механизма. Подмена read
  tool не нужна — перехват вызова и результата (лок-рендер до чтения,
  отдать после); встроенный инструмент не переизобретается;
- сессионные переменные остаются (роль, модель, уровень) — гонка
  сессий за общий файл закрывается локом;
- дети — required-extensions (`registerRequiredChildExtensions`,
  см. §12); herdr не покрывается — принято;
- всё живёт в пределах расширения: правки кода pi не нужны, форк
  отменяется;
- observability: генерируемый `X` рядом с шаблоном, из коробки.

Следствия: пакет A (движок) переезжает без изменений; пакет B
(жизненный цикл) переписывается под рендер-под-локом и `reload`; зона
«правки форка» закрывается.

## 18. Классификация фактов сессии: неявные или объявляемые (@NikolayXHD, @pi-agent)

Тезис @NikolayXHD: недостаточность `{"env": …}` для foreground-детей —
довод против env-источника этой переменной, а не обоснование «неявности».
Классификация «неявная переменная» открыта под вопросом.

Развилка после правки довода (@pi-agent):

- A (текущее решение design.md): факты сессии — зарезервированные имена
  (`model`, `level`, `PI_SUBAGENT_CHILD`), движок кладёт их в view всегда,
  объявление в конфиге — ошибка. Значение гарантированно верно и не
  зависит от конфига; имена и домены — лексика pi (`provider/modelId`,
  `off`…`max`, имя из pi-subagents); шаблоны почти всегда ветвятся по
  `model`/`level` — объявление каждого факта бойлерплейт.
- B: единый класс переменных, у `current` появляется источник факта
  сессии (`{"session": …}`), факты объявляются в конфиге наравне с
  прочими. Одинаковый линт, конфиг самодокументируем, нет
  зарезервированных имён. Цена: конфиг может объявить факт неверно
  (статический `current` вместо источника), движок этого не поймает —
  шаблоны молча свернутся по ложным данным.

Магия имён при B не исчезает: переезжает из имени переменной в строку
факта реестра движка. Разница — в владельце имени и в гарантии значения.
Решение не принято.

## 19. Детекция дочерней сессии: существующие механизмы не покрывают foreground

Исследование (research-child-detection.md) отвечает на требование
@NikolayXHD: не выдумывать имена для чужой области, а найти, как
существующие механизмы детектируют foreground-субагентскую сессию. Ответ:
не детектируют. Факт «сессия — ребёнок» живёт только внутри pi-subagents —
приватный runtime-конфиг (`parentSessionId`, `runId`, `depth`, `nestedParent`),
виден лишь её inline-хукам. Каналы наружу закрыты: env — свойство процесса
фонового раннера; pi не фиксирует происхождение (поле `parentSession`
заголовка заполняется только для `/new`-цепочек и веток, дети создаются
через `SessionManager.create`/`open` без него); биндинг
`registerRequiredChildExtensions` вызывает фабрику ребёнка только со
стандартным `ExtensionAPI`, признака «ты required child» нет; шина событий у
каждой сессии своя, `subagent:child-status` эмитится только хосту. Слабые
признаки (конвенция пути файла сессии, `<active_agent>` в промпте,
`session_info`-имя, отсутствие ambient-расширений) врут в граничных случаях
(in-memory, явные каталоги, fork, переоткрытие файла ребёнка).

Развилка (@pi-agent, решение за @NikolayXHD):

- A — pi-subagents публикует происхождение при создании ребёнка
  существующими средствами pi: поле `parentSession` уже существует и
  читается через `getHeader`, либо запись в сессию пространством имён
  pi-subagents. Мы — потребитель, имена не наши. Цена: правка чужого
  пакета; `parentSession` также заполняется `/new`-цепочками — «есть
  `parentSession`» ≠ «ребёнок».
- B (рекомендация @pi-agent) — два честных признака вместо одного
  составного с заимствованным именем: env `PI_SUBAGENT_CHILD` читается как
  есть (`{"env": …}`, смысл — «процесс — раннер», покрывает фоновых детей)
  плюс свой признак «сессия не основная» (механика design.md, раздел
  «Субагенты»; покрывает foreground-детей и внуков). Скрытие от детей —
  шаблонное условие над двумя признаками (гнездование: в грамматике нет
  or/and). Допущение «ребёнок = не основная» точно по текущей механике:
  foreground-дети стартуют при живой основной сессии, переключения TUI
  закрывают старую перед открытием новой.
- C — отложить условие «скрыть от детей» до сигнала от pi-subagents.

Решение @NikolayXHD: существующего механизма нет — свои не создаём
(вариант A тоже создание механизма — отпадает). Неявная
`PI_SUBAGENT_CHILD`, признак «основная сессия процесса» и шаблонное
условие скрытия роли от детей из design.md удалены. Скрытие контента от
foreground-детей недоступно — ограничение принято. Из существующего
остаётся пользовательский приём: переменная над
`{"env": "PI_SUBAGENT_CHILD"}` (семантика «процесс — фоновый раннер»,
имя переменной вводит автор конфига) и грубая альтернатива — настройка
наследования контекста агентов pi-subagents (`inheritGlobalContext`,
`inheritProjectContext`). Развилка §18 сужается до `model`/`level`.

## 20. Полнота шаблонизации в субагентах; роль — частный случай (@NikolayXHD)

Тезис @NikolayXHD: шаблоны работают в субагенте — или задача с
шаблонами выбрасывается на помойку; третьего не дано. Оценка @pi-agent
«выбрал бы шаблоны» неверна. Субагент не получает переменных родителя:
у него свои значения `model`/`level`, свои сессионные переменные — это
распространяется и на `role`, потому что роль — частный случай
сессионной переменной: вся задача — растворить её в механизме шаблонов
как частный случай. Сессия субагента стартует с собственными
независимыми сессионными переменными; расширение в ней присутствует
обязательно (иначе контекст сломан), значит отрабатывает общий механизм
инициализации и переменная `role` получает дефолтное значение. Чему оно
равно — пустое, непустое или зависящее от `PI_SUBAGENT_CHILD` —
решение пользователя, не зона расширения.

Выводы (@pi-agent):

- механика «скрытия от детей» и детекции дочерней сессии из дизайна
  убираются целиком: проблема растворяется жизненным циклом
  переменных (дети стартуют с дефолтами, переопределения родителя не
  наследуются);
- промпты агентов (`agents/*.md`) включаются в шаблонизацию на общих
  основаниях, полная семантика переменных; ограничений вида «только
  машинные значения» нет; view промпта — view сессии-получателя
  (ребёнка) по общему правилу; точка потребления — построение промпта
  ребёнка (спавн), лок-скобка как у прочих потребителей;
- сценарии, неспособные развернуть шаблоны (herdr-дети, machine,
  внешние CLI), ломают контекст: пользователь не пользуется фичами,
  ломающими контекст.

## 21. Запуски без расширения: best effort, не гейт (@NikolayXHD)

Уточнение @NikolayXHD к §20: запуски, не способные грузить расширения,
не отвергаются. Поскольку файлы не битые (зеркало — последний
отрендеренный текст, см. «Провал рендера»), запуск получает связный
контекст, валить его не нужно. Политика — best effort: расширение
старается, чтобы пользователь осознавал вход в ситуацию, где
разворачивание шаблонов не сработает. `requireForAllRunners` в
дизайне не используется.
