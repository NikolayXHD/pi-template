# 20 — Дизайн: роли и сниппеты на Mustache

## Цель

Роль — Mustache-шаблон, и условия включения фрагментов живут в самих
шаблонах: view несёт данные текущей пары (провайдер, модель, уровень
мышления), секции `{{#имя}}` и `{{^имя}}` включают и выключают текст.
Сниппеты из `roles/snippets/` подставляются тегом `{{> имя-файла}}`.
`roles.json` хранит стартовую роль и список `cycle`. Правки источников
и смена пары применяются к следующему ходу без `/reload`.

Постановка и интервью: `issue.md`, `interview.md` в этой же директории.

## 4.1. Исходное состояние

Расширение собирало текст роли из markdown-источников: `roles/<роль>.md`
содержал директивы `@<файл>.md`, `expandRefs` (extensions/roles/materialize.ts)
подставлял содержимое файла, найденного по basename в `roles/` или её
подкаталогах (`resolveRefPath`), результат писался в
`roles/materialized/<роль>.md` и уходил в system prompt.

Промежуточная версия этой же задачи держала условия в конфиге: записи
`template_variables` с областями (модель, уровень) и флагами, варианты
`materialized/<запись>/<роль>.md`, алгебру списков. Решение отменено
в пользу условий в шаблонах (интервью, пункт 25), конфиг и алгебра
удаляются.

## 4.2. Решения

### Что видит шаблон

На каждый ход расширение кладёт во view данные текущей пары:

- `provider` — имя провайдера: `{{#provider.deepseek}}…{{/provider.deepseek}}`;
- `thinking` — уровень мышления: `{{#thinking.high}}…{{/thinking.high}}`;
- `model` — id модели: `{{#model.deepseek-flash}}…{{/model.deepseek-flash}}`.

Совпадение точное: секция рендерится при равенстве имени текущему
значению, инверсная секция — при отличии. Имя в теге пишется ровно так,
как выглядит значение.

`model` укладывается вложенно по точкам, потому что Mustache читает точку
в теге как путь: id `vllm/QUASAR-QAT/Qwen3.8-27B-QUASAR-NVFP4` пишется
в теге целиком (`{{#model.vllm/QUASAR-QAT/Qwen3.8-27B-QUASAR-NVFP4}}`),
а разложение по точкам делает этот путь рабочим.

### Составные условия

«И» — вложение секций:

```mustache
{{#provider.deepseek}}{{#thinking.high}}…{{/thinking.high}}{{/provider.deepseek}}
```

«ИЛИ» — перечисление секций с тем же текстом:

```mustache
{{#provider.foo}}…{{/provider.foo}}{{#provider.bar}}…{{/provider.bar}}
```

Именованных групп значений в конфиге нет (интервью, пункт 27).

### Роль и сниппеты

- `roles/<роль>.md` — Mustache-шаблон роли.
- `roles/snippets/*` — обычные файлы; все подставляются как partials,
  имя partial — буквальное имя файла (`{{> tests.md}}`). Условность
  задаёт автор, оборачивая фрагмент в секцию внутри файла.
- Mustache используется целиком: `{{# }}`, `{{^ }}`, `{{! }}`, `{{= }}`,
  partials, интерполяция. Лямбд нет.
- Отсутствующий или выключенный фрагмент даёт пусто.

### `roles.json`

```json
{
  "default": "preflight",
  "cycle": ["design", "preflight", "develop", "plan"]
}
```

Разбор строгий: файл — объект; известные ключи `default` и `cycle`;
`default` — непустая строка, `cycle` — массив строк; неизвестный или
пустой ключ — ошибка. Файла нет — материализация создаёт заготовку с
синхронизированным `cycle`. Других настроек у расширения нет.

### Материализация

- Условия зависят от конкретной пары, поэтому рендер идёт под текущие
  модель и уровень, а дерево — `roles/materialized/<роль>.md`. Дерево
  отражает то, что попало в промпт под последнюю отрендеренную пару.
- Проход атомарен через каталог-черновик `roles/materialized.draft/`:
  успешный проход подменяет дерево переименованием
  (`materialized/` → `materialized.previous/`, черновик →
  `materialized/`, затем `previous` удаляется). Провал рендера удаляет
  черновик и оставляет прежнее дерево: роль живёт текстом прошлого
  успешного рендера. Оборванная подмена разбирается на входе прохода:
  остатки черновика удаляются; если есть и `materialized/`, и
  `previous/` — вытесненное дерево удаляется; если `materialized/` нет,
  а `previous/` есть — дерево возвращается на место.
- Проход проверяет имена секций: имя вне словаря условий (`provider`,
  `thinking`, `model`) — предупреждение с именем файла.
- CLI `materialize` принимает пару аргументами:
  `node materialize.ts <agentDir> <provider/id> <уровень>`; цель
  Makefile передаёт их переменными.

### Горячее применение

- Входы: `roles.json`, `roles/*.md`, `roles/snippets/*` и текущая пара.
- В `before_agent_start` сравниваются снапшот файлов и текущая пара;
  различие запускает материализацию, после которой снапшот и пара
  пересобираются. При отвергнутом конфиге снапшот остаётся прежним:
  полузаписанное чтение не закрепляется, и правка применяется после
  починки. Провал рендера снапшоту не мешает.
- `/reload` для правок входов не нужен; `settings.json` во входы
  не входит.

### Активация и наблюдаемость

- Активная роль выбирается в порядке `persisted` → `--role` →
  верхнеуровневый `default`; `Ctrl+R` листает `cycle`, `/role`
  открывает меню и переключает роль явно. На resume имя роли берётся
  из записи сессии, а текст читается из свежего рендера текущей пары.
- Вариант — файл `roles/materialized/<роль>.md`; пара учтена при
  рендере, поэтому активация только читает файл.
- Свежий вариант не собрался — отвергнутый конфиг, отсутствие файла,
  провал рендера — предупреждение, а промпт, статус, запись сессии
  и событие остаются от предыдущего успешного состояния. На старте
  сессии, где предыдущего состояния нет, роль просто не применена.
- Событие `roles:active` шлётся при применении и смене варианта:
  `{name, path}`. Тем же набором пополняется запись сессии `role`.
- При отвергнутом конфиге `Ctrl+R` молчит, `/role` перечисляет роли
  каталога и применить их не может, Tab в меню не работает.

### Ошибки

- Все предупреждения дедуплицируются по тексту; память сбрасывается на
  `session_start` и при принятии нового снапшота.
- Отвергнутый конфиг: предупреждение, роль не сбрасывается, дерево
  и `cycle` не переписываются.
- Провал рендера: предупреждение с именем файла, дерево прежнее.
- Имя секции вне словаря условий: предупреждение с именем файла.

### Миграция

- `roles/*.md`: `@x.md` → `{{> x.md}}`; поддержки `@` не остаётся.
- `roles.json`: ключ `template_variables` убирается, условия переезжают
  в шаблоны.
- Дерево вариантов по записям заменяется деревом по ролям
  (`materialized/<роль>.md`); старые каталоги исчезают при первой
  подмене.
- Обновляются шапка `index.ts`, `probe.mjs`, `TESTING.md`.

## 4.3. Фолбэки

- Отсутствующий или выключенный фрагмент → пусто: штатная семантика
  Mustache, она же семантика постановки «флага нет — подстановка пустая».

## 4.4. План реализации

1. `extensions/roles/config.ts`: `default` и `cycle`, строгий разбор,
   заготовка при отсутствии файла. Без модульного состояния.
2. `extensions/roles/render.ts`: сборка view из пары, `listSnippets`,
   `renderRole`; Mustache только здесь.
3. `extensions/roles/materialize.ts`: проход рендера под пару,
   черновик и подмена дерева, разбор оборванной подмены, синхронизация
   `cycle`, CLI с парой аргументами.
4. `extensions/roles/index.ts`: снапшот файлов и пары, активация,
   статус, событие `{name, path}`, шапка файла.
5. Миграция `roles.json` и ролей.
6. `probe.mjs` и `TESTING.md`.

## Проверка

Кейсы, детальный дизайн тестов — отдельным шагом: view и точные имена
(`provider`, `thinking`, `model`), инверсные секции, «И» вложением
и «ИЛИ» перечислением, вложенный по точкам id, partials и отсутствующий
partial, рендер под пару и замена дерева, атомарность прохода, разбор
оборванной подмены, синхронизация `cycle`, горячее применение по
снапшоту и паре, отвергнутый конфиг, предупреждение об имени секции вне
словаря, миграция директив.
